# 예상문제 정답·해설지 (풍부한 해설 + 누락 0 검수 + 깃허브 배포)

## 왜 만든 스킬인가
대량으로 만들다 보니 문항이 중간중간 빠져서("선생님 중간중간 답이 없어요") 학생 누락 신고가 많았다. 그래서 **만드는 것보다 '빠짐없음 증명'이 더 중요**하다. 검수를 통과하지 못한 파일은 절대 배포하지 않는다.

## 0. 시작 전: 필요한 원본 자료를 먼저 말한다
작업을 시작하기 전에 사용자에게 아래를 먼저 알려 주고, 없는 것이 있으면 시작 전에 요청한다(작업 중간에 없다는 걸 알게 되면 안 됨).
1. 학생에게 실제 배부한 **문제지 원본**(hwp/hwpx/pdf) — 문항 번호의 기준
2. **정답표**(출판사 답안지 또는 선생님 정답) — 정답의 기준. 없으면 풀이로 정답을 만들되 "정답 미확인"이라고 표시
3. **본문 원문**(영어 지문 + 한글 해석이 있으면 함께) — 근거 문장 인용용
4. 총 문항 수(학생 인쇄물의 마지막 번호)와 학교·학년·과(예: 금천고1 3과)

## 1. 문항 목록 먼저 확정 (명부 만들기)
- 문제지에서 문항 번호를 전부 추출해 `명부.json`을 만든다: {번호, 유형, 정답기호}.
- 총 문항 수가 학생 인쇄물 마지막 번호와 일치하는지 먼저 확인. 하나의 지시문 아래 여러 답을 요구하면 1문항, 지시문이 독립 반복되면 각각 별도 문항(friendly-answer-key 스킬의 번호 규칙과 동일).
- 이후 모든 단계는 이 명부를 기준으로 한다. 명부에 없는 번호를 임의로 만들지 않고, 명부에 있는 번호는 하나도 건너뛰지 않는다.

## 2. 문항별 해설 내용 (모든 문항 동일 구조, 하나도 생략 금지)
문항마다 아래 5가지가 **전부** 있어야 한다.
1. **문제 번호 + 유형**
2. **정답** (원문 기호 그대로 ❶❷… / ①②…)
3. **선택지 오지선다 전부 표기: 영어 선택지 뒤에 한글 뜻을 늘 괄호 안에 넣기.** 예) ① although (비록 ~이지만). 선택지가 문장이면 문장 전체의 한글 해석을 괄호로. 한글 뜻 없는 영어는 어디에도 두지 않는다.
4. **답의 근거 문장: 본문에서 근거가 되는 영어 문장을 그대로 인용하고, 바로 아래/뒤에 한글 해석을 늘 같이 쓴다.** (영어만 달랑 인용 금지)
5. **풍부한 해설**: 사전식 뜻풀이(어원·품사)가 아니라, 본문을 읽어 가며 내용이 기억나게 하는 설명 — 문장 흐름, 앞뒤 연결, 헷갈리는 구조, 왜 정답이고 나머지 선택지는 왜 아닌지(오답마다 한 줄, 한글 뜻 괄호 포함).

## 3. 서식 (SJ 선호)
- 표 사용 금지. 큰 글씨의 일반 문단, 왼쪽 정렬. 깨알 글씨 금지.
- 학생용 화면에서 영어가 나오면 반드시 한글 뜻이 함께.
- 어려운 개발자 용어 쓰지 말고 쉬운 말로.
- 각 문항 카드 맨 위에 문항 번호를 크게 표시. 모든 번호에 `id="q12"` 같은 앵커를 달고, 상단에 번호 바로가기 목록(1~N)을 둔다.

## 4. 만드는 방식 (대량 작업)
- 명부 기준으로 10~20문항 단위 묶음으로 나눠 `data_01.json`, `data_02.json` … 로 저장. 서브에이전트에 위임할 때는 (a) 정확한 번호 범위, (b) 위 5요소 스키마, (c) "범위 안의 모든 번호를 빠짐없이, 건너뛰지 말고" 지시를 반드시 포함.
- 최종 HTML은 `build.py` 하나가 모든 data 파일을 합쳐 조립한다(손으로 이어붙이다 빠지는 사고 방지).

## 5. ★ 누락 검수 (필수 · 통과 전 배포 금지)
**1단계 – 기계 검수 (코드로, 예외 없이)**
- 명부의 번호 1~N 전부가 최종 HTML에 `id="qN"`으로 정확히 1번씩 있는지(누락·중복 0).
- 각 문항 카드에 5요소가 있는지: 정답 기호 / ①~⑤ 다섯 선택지 전부 / 선택지마다 한글 괄호 / 근거 영어 문장 + 한글 해석 / 해설 본문. 하나라도 비면 번호를 목록으로 출력.
- 정답 기호가 정답표와 100% 일치하는지 자동 대조.
- 영어 문자열 뒤에 한글이 없는 곳(영어만 있는 줄) 검출.
- 빈 문자열, "TODO", "…", "생략", "위와 동일" 같은 자리표시 문구 검출.
- 결과를 `검수결과.txt`에 남긴다(총 N문항, 누락 0, 중복 0 등).

**2단계 – Opus 검수 (반드시, 비용 신경 쓰지 말 것)**
- Agent 도구로 `model: "opus"` 서브에이전트를 띄운다. 만든 사람(작성 에이전트)과 다른 눈으로 보게 하기 위해 작성 과정은 알려 주지 말고 **문제지 원본 + 정답표 + 최종 HTML 파일 경로만** 준다.
- 지시: "문제지의 모든 문항 번호를 하나씩 해설지와 대조하라. 누락·중복·번호 밀림, 선택지 한글 뜻 누락, 근거 문장의 한글 해석 누락, 정답 불일치, 해설 내용이 문제와 안 맞는 경우를 문항 번호별로 전부 보고하라. 일부만 샘플링하지 말고 전수로 하라. 문제 없으면 '전수 확인 N/N' 이라고 적어라."
- 문항이 많으면(60문항↑) 범위를 나눠 Opus 여러 개에 병렬 위임하되 범위가 겹치지 않고 전체를 덮는지 확인.
- Opus가 문제를 하나라도 보고하면: 수정 → build.py 재실행 → 1단계부터 다시. **연속 2회 무결점 통과해야 합격.**

## 6. 배포: 깃허브 링크 하나로만 (네이버 카페 사용 안 함)
- 고등 자료는 via-high 저장소 `h/<학교>/…`, 중등은 via-mid. 학교마다 따로 주소를 두고 전체 학교 모음 페이지는 만들지 않는다(학생에게 자기 학교 것만 넘김). 선생님용 모음/메뉴판은 학교·학년별 목록 한 장에서 정답마다 개별 페이지로 연결(하나 고칠 때 여러 개를 건드리지 않게).
- 해설지 전체(1~N문항)를 **한 링크 안에** 넣는다. 번호 바로가기를 맨 위에 둔다.
- 폴더·파일 이름 앞에 최신 날짜 YYMMDD를 붙인다(예: 261018_금천고1_3과_예상문제해설). 재작업 시 이전 것은 OLD로 구분.
- 같은 문서가 두 군데 생기지 않게: 결과물은 지정 폴더에 한 부만 두고 폴더 밖 중복본은 지우거나 위치를 알린다. 깃허브 업로드 후에는 USB/PC 보관 사본 위치도 알려 준다(나중에 고치기 쉽게).
- 업로드 후 **실제 공개 링크를 열어** 총 문항 수(앵커 개수)가 N인지 한 번 더 확인하고 링크를 전달한다(깃허브 페이지 반영에 1~2분 걸릴 수 있음).

## 7. 최종 보고
사용자에게는 짧게: ① 링크 ② 총 N문항 · 누락 0 · Opus 전수 검수 통과(회차) ③ 정답 미확인/보기 유실 등 예외가 있으면 번호로 명시. 작업 과정 나열은 하지 않는다.

## 8. 하지 않는 것
- 일부 문항을 "비슷하니 생략", "나머지도 같은 방식"으로 줄이기
- 원문에 없는 보기·본문을 지어내기(유실되면 '보기 유실' 표시하고 확인 요청)
- 검수 통과 전 링크 전달
